# Лабораторная работа №2

## Назначение работы

Лабораторная работа нужна для изучения интеграционного тестирования на примере программы, которая вычисляет систему математических функций. Основная идея работы: сначала проверить отдельные модули, а затем проверить, что они правильно работают вместе при постепенной интеграции.

Вариант: `731348`.

Система функций состоит из двух частей:

- при `x <= 0` вычисляется тригонометрическое выражение через `sin`, `cos`, `tan`, `cot`, `sec`, `csc`;
- при `x > 0` вычисляется логарифмическое выражение через `log3`, `log5`, `log10`.

## Структура проекта

Основной код находится в `src/main/java/ru/itmo/qa/lab2`.

Основные классы:

- `EquationSystem` - вычисляет итоговую систему функций по варианту.
- `FunctionRule` - общий интерфейс функции с методом `calculate`.
- `AbstractFunction` - базовый класс для функций, содержит общую проверку аргументов и точности.
- `Sine` - базовая тригонометрическая функция, реализована через ряд.
- `NaturalLogarithm` - базовая логарифмическая функция, реализована через ряд.
- `Cosine`, `Tangent`, `Cotangent`, `Secant`, `Cosecant` - производные тригонометрические функции.
- `BaseNLogarithm` - логарифм по заданному основанию через натуральный логарифм.
- `CSVGraphWriter` - запись значений функции в CSV-файл.

Заглушки находятся в пакете `stub`:

- `SineStub`
- `CosineStub`
- `TangentStub`
- `CotangentStub`
- `SecantStub`
- `CosecantStub`
- `NaturalLogarithmStub`
- `BaseNLogarithmStub`

Они нужны для интеграционного тестирования, чтобы временно заменять реальные модули табличными значениями.

## Как устроены вычисления

Все функции имеют общий метод:

```java
calculate(BigDecimal x, BigDecimal precision)
```

Параметры:

- `x` - аргумент функции;
- `precision` - требуемая точность вычисления.

Базовые функции:

- `Sine` вычисляет `sin(x)` через разложение в ряд Тейлора;
- `NaturalLogarithm` вычисляет `ln(x)` через ряд.

Остальные функции выражены через базовые:

- `Cosine` использует `Sine`;
- `Tangent` использует `Sine` и `Cosine`;
- `Cotangent` использует `Sine` и `Cosine`;
- `Secant` использует `Cosine`;
- `Cosecant` использует `Sine`;
- `BaseNLogarithm` использует `NaturalLogarithm`.

Такое разделение нужно, чтобы можно было тестировать модули отдельно и постепенно собирать всю систему.

## Анализ функции

Перед написанием тестов нужно понять, где функция определена, где у нее особые точки и какие значения стоит брать для проверки.

Система кусочная:

- при `x <= 0` работает тригонометрическая часть;
- при `x > 0` работает логарифмическая часть.

### Тригонометрическая часть

Тригонометрическая часть содержит `tan(x)`, `cot(x)`, `sec(x)` и `csc(x)`. У этих функций есть точки, где они не определены:

- `tan(x)` не определен там, где `cos(x) = 0`;
- `cot(x)` не определен там, где `sin(x) = 0`;
- `sec(x)` не определен там, где `cos(x) = 0`;
- `csc(x)` не определен там, где `sin(x) = 0`.

Поэтому на отрезке от `-2π` до `0` важны точки:

- `x = -2π`;
- `x = -3π/2`;
- `x = -π`;
- `x = -π/2`;
- `x = 0`.

В этих точках или рядом с ними возможны разрывы и вертикальные асимптоты. Поэтому для тестирования выбираются значения из разных промежутков между асимптотами:

- `-6.2`;
- `-6.0`;
- `-5.5`;
- `-4.0`;
- `-3.3`;
- `-2.0`;
- `-1.0`;
- `-0.5`.

Так проверяются разные участки периода функции, а не только одна случайная точка.

### Логарифмическая часть

Логарифмическая часть работает только при `x > 0`, потому что логарифм не определен для неположительных значений.

В самой формуле есть деление на логарифмы:

```text
log3(x) * (log10(x) * log5(x))
```

При `x = 1` все логарифмы равны нулю, поэтому в этой точке возникает деление на ноль. Значит, для логарифмической части важны две особые точки:

- `x = 0` - граница области определения логарифмов;
- `x = 1` - точка, где знаменатель обращается в ноль.

Для проверки выбраны точки:

- `0.1`;
- `0.5`;
- `2.0`;
- `3.0`;
- `8.0`;
- `10.0`.

Они находятся по разные стороны от особой точки `x = 1` и позволяют проверить поведение функции на нескольких участках области определения.

### Эквивалентное разбиение

Метод эквивалентного разбиения означает, что область входных значений делится на группы, внутри которых программа должна вести себя похожим образом. Тогда не нужно проверять бесконечно много значений, достаточно выбрать несколько представителей из разных групп.

В этой лабораторной разбиение строится вокруг:

- области определения функций;
- точек разрыва;
- вертикальных асимптот;
- границы между ветвями `x <= 0` и `x > 0`;
- специальных значений вроде `x = 1` для логарифмов.

Для запрещенных или особых точек проверяется, что программа бросает исключение. Для допустимых точек проверяется, что функция возвращает значение с заданной точностью.

## Тестирование

Тесты находятся в `src/test/java/ru/itmo/qa/lab2`.

Есть два основных типа тестов:

- модульные тесты в пакетах `module`;
- интеграционные тесты в пакетах `integration`.

Тестовые данные находятся в `src/test/resources` в CSV-файлах.

Модульные тесты проверяют отдельные функции на заранее выбранных значениях. Интеграционные тесты проверяют взаимодействие функций между собой: например, что `Tangent` корректно использует `Sine` и `Cosine`, а `BaseNLogarithm` использует `NaturalLogarithm`.

Для подмены зависимостей используются:

- табличные заглушки;
- Mockito-моки.

### Зачем нужны табличные заглушки

Табличная заглушка - это упрощенная замена реального модуля. Она не вычисляет функцию по формуле, а возвращает заранее записанные значения из таблицы.

Например, реальный `Sine` вычисляет `sin(x)` через ряд. Это сложнее и потенциально может содержать ошибку. Для интеграционного теста иногда важно проверить не сам синус, а класс, который от него зависит. Например, `Cosine` использует `Sine`. Чтобы проверить только связь `Cosine -> Sine`, можно вместо настоящего `Sine` подставить `SineStub`.

Смысл такой:

- реальная функция может ошибаться из-за формулы, ряда, округления или особых точек;
- заглушка возвращает известный результат для выбранных точек;
- если тест с заглушкой проходит, значит проверяемый модуль правильно обращается к зависимости;
- если после замены заглушки реальной функцией тест падает, проблема, скорее всего, в реальной реализации или в точности вычисления.

Пример из проекта:

```java
Cosine cos = new Cosine(new SineStub());
```

В этом случае `Cosine` работает не с настоящим `Sine`, а с таблицей значений синуса. Это помогает изолировать тестируемую часть.

Табличные заглушки особенно полезны в этой лабораторной, потому что функции зависят друг от друга:

- `Cosine` зависит от `Sine`;
- `Tangent` зависит от `Sine` и `Cosine`;
- `Cotangent` зависит от `Sine` и `Cosine`;
- `Secant` зависит от `Cosine`;
- `Cosecant` зависит от `Sine`;
- `BaseNLogarithm` зависит от `NaturalLogarithm`.

Если тестировать все сразу, то при ошибке сложно понять, какой именно модуль виноват. Заглушки позволяют подключать систему постепенно.

### Что такое Mockito-моки

Mockito - это библиотека для создания тестовых замен объектов.

Mock-объект - это объект, поведение которого задается прямо в тесте. Он не выполняет настоящую логику класса, а возвращает то, что ему указали вернуть.

Пример:

```java
when(mockLog10.calculate(any(), any())).thenReturn(new BigDecimal("2"));
```

Это означает: когда у `mockLog10` вызовут метод `calculate` с любыми аргументами, он должен вернуть `2`.

Моки нужны, когда требуется полностью контролировать зависимость. Например, в тесте `EquationSystem` можно задать значения `log10`, `log3`, `log5` вручную и проверить, что итоговая формула считает правильно.

Преимущество мока:

- он не зависит от настоящей реализации;
- можно легко задать любые значения;
- можно проверить поведение системы на специальных случаях;
- можно проверить, что метод был вызван.

Например:

```java
verify(mockLog3, atLeastOnce()).calculate(any(), any());
```

Эта проверка означает, что система действительно обращалась к `log3`.

Разница между stub и mock:

| Вид объекта | Что делает | Для чего нужен |
| --- | --- | --- |
| Stub | Возвращает заранее заданные табличные значения | Заменить сложную зависимость простой таблицей |
| Mock | Возвращает значения, заданные прямо в тесте | Полностью контролировать зависимость |

### Как это применяется в лабораторной

В лабораторной есть цепочки зависимостей. Например, итоговая система `EquationSystem` зависит сразу от многих функций. Если тестировать ее только целиком, то при ошибке будет непонятно, где именно проблема: в самой формуле системы, в тангенсе, в синусе, в логарифме или в обработке особых точек.

Поэтому тестирование разделено на уровни:

1. Сначала проверяются базовые функции `Sine` и `NaturalLogarithm`.
2. Потом проверяются функции, которые от них зависят.
3. Потом через mock-объекты проверяется, что зависимости реально вызываются.
4. Потом проверяется вся система.

Такой подход показывает не только правильность результата, но и правильность архитектуры взаимодействия классов.

## Стратегия интеграции

В работе используется подход сверху вниз и постепенная замена заглушек реальными модулями.

В контексте этой лабораторной верхний уровень - это `EquationSystem`, потому что именно он вычисляет итоговую функцию варианта. Ниже находятся отдельные математические модули: тригонометрические и логарифмические функции.

Идея интеграции такая: не подключать все сразу, а двигаться постепенно. Сначала можно подставить вместо зависимостей простые заглушки или моки. Потом по одному подключать реальные классы и проверять, что система продолжает работать.

Общий порядок:

1. Проверяется верхний уровень системы с заглушками зависимых функций.
2. Отдельные заглушки заменяются реальными реализациями.
3. Проверяется корректность взаимодействия между соседними модулями.
4. Проверяется полная система без заглушек.

Такой подход удобен, потому что ошибку проще локализовать: если тест упал после замены конкретной заглушки реальным классом, проблема, скорее всего, находится в этом классе или в его связи с остальной системой.

Пример для логарифмической части:

1. `BaseNLogarithm` проверяется с мокнутым `NaturalLogarithm`.
2. Потом `BaseNLogarithm` проверяется с настоящим `NaturalLogarithm`.
3. Потом `EquationSystem` проверяется с настоящими `log3`, `log5`, `log10`.

Пример для тригонометрической части:

1. `Cosine` проверяется с `SineStub`.
2. `Tangent` проверяется с моками `Sine` и `Cosine`.
3. Потом `Tangent` проверяется с настоящими `Sine` и `Cosine`.
4. Потом вся тригонометрическая ветвь проверяется через `EquationSystem`.

Таким образом, интеграционные тесты отвечают на вопрос: правильно ли классы соединены между собой и правильно ли они используют друг друга.

## Вопросы к защите

### 1. Цели и задачи интеграционного тестирования

Интеграционное тестирование проверяет не отдельный класс сам по себе, а взаимодействие нескольких модулей между собой.

Цели интеграционного тестирования:

- найти ошибки во взаимодействии компонентов;
- проверить корректность передачи данных между модулями;
- проверить совместимость интерфейсов;
- убедиться, что несколько уже протестированных частей вместе работают правильно.

Задачи интеграционного тестирования:

- проверить связи между классами и модулями;
- выявить ошибки в контрактах методов;
- проверить обработку исключительных ситуаций на границах модулей;
- проверить систему при замене заглушек реальными реализациями.

В последовательности тестирования интеграционные тесты обычно идут после модульных тестов и перед системным тестированием.

Обычный порядок:

1. Модульное тестирование.
2. Интеграционное тестирование.
3. Системное тестирование.
4. Приемочное тестирование.

Модульное тестирование проверяет отдельные функции или классы. Интеграционное тестирование проверяет их совместную работу. Системное тестирование проверяет всю систему целиком с точки зрения требований.

### 2. Алгоритм интеграционного тестирования

Типовой алгоритм:

1. Определить модули системы и зависимости между ними.
2. Определить порядок интеграции модулей.
3. Подготовить заглушки или моки для еще не подключенных частей.
4. Написать тесты для проверки взаимодействия модулей.
5. Подключить первый набор реальных модулей.
6. Запустить тесты и проверить результат.
7. Постепенно заменять заглушки реальными модулями.
8. После каждого шага запускать тесты.
9. В конце проверить полную систему без заглушек.

В этой лабораторной сначала проверяются отдельные функции, затем связи вида `Cosine -> Sine`, `Tangent -> Sine + Cosine`, `BaseNLogarithm -> NaturalLogarithm`, а затем вся система `EquationSystem`.

### 3. Концепции и подходы интеграционного тестирования

Основные подходы:

- сверху вниз;
- снизу вверх;
- сэндвич-подход;
- big bang;
- инкрементальная интеграция.

Подход сверху вниз означает, что сначала тестируется верхний уровень системы, а нижние зависимости заменяются заглушками. Потом заглушки постепенно заменяются реальными модулями.

Подход снизу вверх означает, что сначала тестируются низкоуровневые модули, а затем из них собираются более крупные части системы.

Big bang означает, что все модули объединяются сразу. Этот подход проще по подготовке, но хуже для поиска ошибок, потому что при падении тестов сложнее понять, какой именно модуль виноват.

В лабораторной используется инкрементальный подход: система собирается постепенно, а зависимости можно заменять заглушками и моками.

### 4. Программные продукты для интеграционного тестирования. JUnit

Для интеграционного тестирования могут использоваться разные инструменты:

- JUnit для написания и запуска тестов в Java;
- Mockito для моков и проверки вызовов;
- Gradle или Maven для автоматического запуска тестов;
- JaCoCo для оценки покрытия тестами;
- Testcontainers для тестов с внешними сервисами, например БД или брокерами сообщений;
- CI-системы для автоматического запуска тестов после изменений.

В этой лабораторной используются:

- JUnit 5;
- Mockito;
- Gradle;
- JaCoCo.

JUnit используется для описания тестовых методов, параметризованных тестов и проверки результатов через assertions. Mockito используется для подмены зависимостей и проверки, что нужные методы действительно вызываются.

Пример интеграционного теста в проекте: `EquationSystemIntegrationTest`. Он проверяет, какие модули вызываются при `x <= 0` и при `x > 0`, а также проверяет работу системы с моками и реальными функциями.

### 5. Автоматизация интеграционных тестов

Автоматизация интеграционного тестирования нужна, чтобы тесты можно было запускать регулярно и без ручной проверки.

Преимущества автоматизации:

- быстрое обнаружение регрессий;
- одинаковый способ запуска тестов;
- возможность запускать тесты после каждого изменения;
- удобная проверка проекта перед сдачей или релизом.

В этом проекте автоматизация сделана через Gradle:

```bash
./gradlew test
```

Gradle компилирует проект, запускает JUnit-тесты и формирует отчет о покрытии через JaCoCo.

Для полноценной автоматизации в реальном проекте такие тесты обычно запускаются в CI, например GitHub Actions, GitLab CI или Jenkins.

В лабораторной реализована система функций по варианту, базовые функции через ряды, производные функции через базовые, табличные заглушки и интеграционные тесты. Основной результат работы - проверка того, что отдельные математические модули корректно объединяются в единую систему.
